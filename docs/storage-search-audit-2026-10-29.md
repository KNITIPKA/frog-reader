# Аудит хранения, поиска и BackupArchive v4 — 29 октября 2026

Проверялся текущий исходный код, включая незакоммиченные изменения. SQLite/Room, единая база, существующая модель `Book` и формат архива v4 сохранены. Поддержка JSON-хранилищ и архивов v1–v3 не возвращалась. Приложение ещё не опубликовано; подготовка к чистой установке допустима. Для будущей эволюции SQLite оставлен небольшой штатный пример миграции Room v1→v2: он пересчитывает только производные FTS-индексы после исправления нормализации.

## Что подтверждено и сохранено

- Room 3 + bundled SQLite, WAL, один writer и пул readers; Room включает foreign keys на каждом соединении. Удалена ручная установка `synchronous=NORMAL` для standalone-снимков: выбор режима оставлен Room, который использует FULL вне WAL.
- `doc_id INTEGER PRIMARY KEY AUTOINCREMENT`, уникальный доменный `id`, индексы внешних ключей, ACID save/delete содержания вместе с FTS. `REPLACE` и destructive fallback не добавлялись.
- Частые записи прогресса/времени не переиндексируют весь каталог. Целевые изменения поисковых полей обновляют только соответствующие FTS-строки. Полная перестройка производится при штатной миграции индекса.
- Латиница/кириллица ищутся по началу слова; AND может охватывать разные поля. Арабские/ивритские клитики проверяются Kotlin после отдельного набора кандидатов. FTS-операторы экранируются.
- Порядок библиотеки: Title > Author > Series > Description, затем сила whole-word/prefix/clitic, затем прежний порядок библиотеки. Вычисленный bm25 не меняет этот последний критерий. Профиль сохраняет bm25 ASC при равной силе совпадения; отрицательные bm25 правильно сортируются по возрастанию.
- Debounce не добавлялся без необходимости: `mapLatest` отменяет прежний поиск, внутри долгих проходов проверяется отмена. Подсветка проверена в UTF-16, включая surrogate pairs, combining marks и арабские/ивритские огласовки.
- Старые JSON-файлы не читаются, не мигрируются и автоматически не удаляются при запуске. Архивы старых форматов по-прежнему отклоняются.

## Что содержит архив и что переносится

| Данные | DATA | FULL |
| --- | --- | --- |
| Согласованный SQLite snapshot, библиотечные метаданные, прогресс, полки, passages, очередь/журнал, статистика/достижения и FTS | Да | Да |
| Reader/app settings, профиль/аватар | Да | Да |
| Пользовательские шрифты из `files/fonts` | Да | Да |
| Обложки/фото Reading Log | Да | Да |
| Импортированные EPUB/PDF/TXT/MD и другие локальные файлы библиотеки, приватные вложения очереди | Нет | Да, если исходный файл существует |
| Обложки книг/очереди | Нет | Да |
| Права Android SAF, выбранная папка scheduled backup, расписание, локальный device ID | Нет | Нет |
| Кэш распарсенных книг/рендеринга, произвольные внешние пользовательские каталоги | Нет | Нет |

Импортируемые книги копируются внутрь приложения; перенос не зависит от исходного SAF URI. Права доступа Android к внешней папке между устройствами не переносятся: папку резервного копирования нужно выбрать заново. Абсолютные пути собственных шрифтов преобразуются в `fonts/<name>` и возвращаются в целевой каталог; коллизии при restore учитываются. Несуществующие исходные файлы FULL-экспорт по прежнему может пропустить; при восстановлении недоступные книги отражаются в `booksWithoutFile`, метаданные и passages сохраняются. Архив v4 не содержит криптографического manifest всех assets, поэтому отличить намеренно отсутствовавший исходник от вручную удалённого ZIP-entry невозможно.

## Пределы подтверждения и дальнейшие задачи

- Проверка восстановления после завершения процесса моделирует его состояние на диске; физическое отключение питания и перебор каждого машинного шага не выполнялись. Файлы синхронизируются, но отдельной гарантии сохранения directory entries при потере питания без fsync каталога нет.
- Реальное заполнение пользовательского накопителя до ENOSPC намеренно не выполняется. Порядок copy-before-swap, неподавленные I/O-ошибки и сохранение rollback-копии уменьшают этот риск; отказ файловой системы в любой точке требует отдельного стенда.
- После прерванного restore могут остаться новые, ещё не используемые asset-файлы. Они не заменяют прежние данные, но занимают место. Старые файлы не удаляются агрессивно в критической фазе восстановления.
- Результаты широкого поиска пока материализуются целиком, память растёт с числом совпадений. Это подтверждённая граница масштабирования; произвольный LIMIT не введён, поскольку он незаметно терял бы результаты и менял UX. Для существенно больших библиотек следующим самостоятельным изменением должна быть полноценная пагинация с сохранением ранжирования.
- `instr()` для клитик остаётся линейным проходом. Новый специализированный индекс не добавлялся: текущие измерения не оправдывают его сложность.
- Ни host-native SQLite, ни два узких Android-теста не заменяют полный пользовательский прогон всех экранов, жестов, Accessibility и проверки release APK на устройстве.

## Архитектурный вердикт

Единая Room/SQLite-БД и стабильные doc_id — пригодная основа для дальнейшего развития. Основные подтверждённые проблемы были в границах операций восстановления, синхронизации состояний и эквивалентности поиска, а не в выбранной архитектуре. Переписывание хранилища или возврат legacy-слоёв не требуется. Готовность к распространению следует оценивать с указанными ограничениями по power-loss, очень большим поисковым выдачам и полноценному device/release QA.

## Первичные источники

Поведение `VACUUM INTO`, WAL/sidecars и FTS проверялось по [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html), [SQLite о journal/WAL и безопасном копировании](https://www.sqlite.org/howtocorrupt.html), [SQLite FTS5](https://www.sqlite.org/fts5.html), а поведение Room — также по исходникам установленной Room 3.0.3 (`RoomConnectionManager.kt`: конфигурация соединений, проверка identity, onValidateSchema, миграции). Работа ведётся со штатными API Room/SQLite.
